代码 · R1 票款背离

R1：只看 11 表，两方比对

D1 = |B2 − S2|
B2 累计发票金额　S2 累计支付金额
命中 = D1 > 10,000 元 且 D1 ÷ MAX(B2,S2) > 5%
评分 = MIN(100, 差异率 ÷ 25% × 100)

为什么必须双门槛：
只看绝对额，1 亿的合同差 30 万会被报；
只看相对率，100 万的合同差 4.9 万会被放过。
def rule_r1(f, p):
    b2, s2 = f["b2"], f["s2"]
    if b2 is None or s2 is None:
        return None
    diff  = abs(b2 - s2)
    ratio = ratio_of(diff, max(b2, s2))
    # 两道门槛必须同时越过
    if diff <= q2(p["tolerance_amount"]) \
       or ratio <= D(str(p["tolerance_ratio"])):
        return None
    sc = score_of(ratio)
    direction = "付款大于开票" if s2 > b2 else "开票大于付款"

方向本身就是信息：款多查开票，票多查账期
代码 · R2 累计结算超合同额

R2：只看 16 表，方向性判定

D4 = E1 − C1（保留正负号）
E1 已结算金额　C1 合同总金额
命中 = D4 > 10,000 元 且 D4 ÷ C1 > 5%
评分 = MIN(100, 超合同率 ÷ 25% × 100)

负数是正常的：合同还没结算完。
所以这条只查超、不查少，over <= 0 直接返回。

两个字段规范都写明「非框架合同填写」，框架过滤不能省。
def rule_r2(f, p):
    c1, e1 = f["c1"], f["e1"]
    over = e1 - c1
    if over <= 0:          # 未超，正常状态
        return None
    ratio = ratio_of(over, c1)
    if over <= q2(p["tolerance_amount"]) \
       or ratio <= D(str(p["tolerance_ratio"])):
        return None
    sc = score_of(ratio)
    return dict(rule="R2", diff=over, ratio=ratio,
                score=sc, level=level_of(sc), ...)
完整实现见 code/run_model.py 第 155–171 行
评分与等级由同一函数派生，不会出现「61 分却高风险」
代码 · SQL 侧

同一套规则，SQL 再写一遍

SQL 负责清洗与特征，Python 负责规则；两边独立实现，结果必须一致。
-- 02_feature.sql：一份合同一行
SELECT c.CONTRACT_CODE, c.CONTRACT_AMOUNT AS c1,
       c.SETTLEMENT_AMOUNT AS e1,
       i."累计发票金额" AS b2,
       i."累计支付金额" AS s2
FROM dwd_contract_clean c
LEFT JOIN dwd_invoice_latest i
  ON c.CONTRACT_CODE = i."合同编号";
清洗层先剔框架、剔外币、剔状态 3、取最新版本
c1 / e1 / b2 / s2 是特征表列名，分别对应合同额、已结算、累计发票、累计支付
-- 03_rule_preview.sql：R1
WHERE b2 IS NOT NULL AND s2 IS NOT NULL
  AND MAX(b2, s2) > 0
  AND ABS(b2 - s2) > 10000
  AND ABS(b2 - s2) * 1.0 / MAX(b2, s2) > 0.05;

-- R2
WHERE c1 > 0
  AND (e1 - c1) > 10000
  AND (e1 - c1) * 1.0 / c1 > 0.05;
Hive 版用 GREATEST 取两值较大者，SQLite 版用 MAX；逻辑等价

输出 · 字段设计依据

为什么非要这些字段

不是为了好看，是流程指导里明确要求：输出要能支撑排查与管理两类动作。

共性字段 · 管模型

线索 ID、模型编码、风险类型、风险分、风险等级

用途：线索追踪与闭环管理、模型版本回溯、阈值调整后重算、人工复核优先级排序

溯源字段 · 找到人

合同编号、成员单位名称与代码、数据来源

用途：风险定位与归属，知道该找哪家单位、哪份合同核对

个性字段 · 说清事

金额、差异率、差异方向、证据集与明细

用途：可解释、可复算、可取证，复核时能直接定位原始记录

《定制化模型研发流程指导》3.2 模型输出数据：“模型输出字段除风险直接相关字段外，还应包括用于风险排查和模型管理的辅助字段。 建议包含共性字段（线索 ID、场景类型、模型编码、模型风险分、模型风险等级）、溯源字段（所属集团名称、所处成员单位名称、采购单号 ID）和个性字段（本项目具体的证据项）。”
落到我们的四张表上：共性 → Risk Candidate 的前 5 列（candidate_id 到 risk_level）； 溯源 → Candidate 的合同编号与成员单位、Evidence 的 source_record_id； 个性 → Business Fact 的金额与比率、Evidence 明细里的源字段取值。
少一类字段，就会有一类问题答不上来：缺共性没法排序，缺溯源不知道找谁，缺个性没法复核

收尾 · 边界与提问

三句话交代边界

看不到「应付」

R1 只比票与款。应付已确认而票、款都没发生，差额为 0，本模型不报——那属于应付挂账。

红冲口径待确认

11 表累计发票金额是否已剔除红冲，规范未明确。若含红冲，B2 会虚高，产生「多开票」误报。

阈值是演示值

1 万元 + 5% 来自内控经验，不是条文。真实场景须用 POC 核查结论回标。
